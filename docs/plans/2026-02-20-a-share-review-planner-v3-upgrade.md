# A股复盘 Skill 升级方案 v3（性能优先 + 三类资金数据）

> 文档版本：v3.0
> 日期：2026-02-20
> 关联文档：`docs/plans/2026-02-20-a-share-review-planner-v2-upgrade.md`
> 目标：在不扩大系统复杂度的前提下，优先提升分析吞吐与选股质量

---

## 一、决策背景

基于 `github_cache/a-share-research/SYNTHESIS_REPORT.md` 与 `analysis_batch1-5.md` 的横向对比，外部项目给出的方向很多（多源降级、MCP、多Agent、龙虎榜、采样压缩等）。

但当前阶段最关键约束是：

1. 每日复盘有时长预算，深度分析阶段已成为主耗时点。
2. 选股质量对用户价值高于数据源“看起来更全”。
3. 过早引入大规模主备数据源，会显著增加维护成本与故障面。

因此本次 v3 采用明确取舍：

- 先做性能，再做高价值资金信号。
- 暂不优先做全链路主备数据源改造。

---

## 二、修改动机（Why）

### 2.1 为什么先优化性能

现有工作流中，第3.5步（个股深度分析）包含多股票串行采集 + compact/brief 生成，具备明显耗时累积效应。

如果不先优化性能：

1. 即使新增更多因子，日报出具时间也会不可控。
2. LLM 输入体积继续增长，稳定性下降。
3. 后续任何能力扩展都会放大延迟问题。

所以 v3 将“并行化、限流、截断、可观测”作为第一优先级。

### 2.2 为什么先落地三类资金数据

对当前“趋势 + 题材”定位而言，资金维度是最能直接提升选股质量的信号层。

本次优先三类：

1. 北向资金（个股维度）
2. 主力资金（个股净流入）
3. 龙虎榜资金（机构/游资动向）

动机是把“热度驱动”改为“热度 + 资金确认”，减少追高与伪热点。

### 2.3 为什么暂缓主备数据源

主备数据源是工程正确方向，但当前不是首要矛盾。

1. 当前已有 `data_degraded` 风险标记，可在缺失数据时降级分析，不会静默伪造数据。
2. 全链路主备改造涉及多个 fetcher、一致性校验、字段归一化，短期回报低于性能与资金因子。
3. v3 目标是“先把同样时间内的决策质量做上去”，而不是“先扩充采集表面覆盖度”。

---

## 三、v3 目标与范围

### 3.1 本次必须完成（In Scope）

1. 性能优化（第3.5步）
   - 候选股深度分析并行执行
   - 增加并发上限与超时控制
   - 增加阶段耗时日志与单票耗时日志

2. Token/体积控制
   - `compact` 输入条数上限
   - 正文长度截断
   - 时间降采样策略（最近窗口全量，早期抽样）

3. 三类资金数据接入与融合
   - 北向个股净买入（非仅总量）
   - 主力资金候选股映射增强
   - 龙虎榜资金信号接入
   - 在四因子评分中新增资金加分规则（文档 + 字段）

4. 文档与协议同步
   - 更新 `references/analysis-framework.md` 评分规则
   - 更新 `references/commands.md` 输出字段说明
   - 更新 `schema_v1.json` 与 `validate_output.py` 对应字段（若新增必填字段）

### 3.2 本次不做（Out of Scope）

1. 全量主备数据源适配层（金融界→AKShare→腾讯/新浪）
2. mcp-cn-a-stock 深度集成到主流程
3. 多Agent辩论式架构改造
4. UI/可视化改造

---

## 四、实施原则

1. 质量优先于覆盖：新增数据若质量不稳定，宁可标记降级，不强行入模。
2. 稳定优先于功能：每个新增信号都必须有失败兜底，不阻断主流程。
3. 复杂度受控：优先在现有脚本上渐进扩展，不引入大型新框架。
4. 可验证：每个改动点必须可通过单元测试或脚本自测验证。

---

## 五、阶段计划

### Phase A：性能基线与瓶颈治理

1. 为第3.5步建立耗时统计（总耗时/单票耗时/失败率）
2. 引入并行执行 + 限流 + 超时
3. 验证同等候选数量下总耗时下降

### Phase B：三类资金信号落地

1. 设计统一资金字段模型（northbound/main_force/lhb）
2. 接入并写入采集产物
3. 在筛选评分中加入资金确认项
4. 回归验证：无资金数据时仍能降级运行

### Phase C：文档与校验收口

1. 更新分析框架与命令文档
2. 更新 schema 与校验脚本
3. 增补测试样例（含缺失/降级/异常格式）

---

## 六、验收标准

### 6.1 性能

1. 第3.5步总耗时较当前基线显著下降（同样候选数）
2. 出现单源失败时不阻断整轮复盘
3. 日志可定位到具体慢点（步骤/股票）

### 6.2 质量

1. 候选评分中可追溯三类资金信号来源
2. `candidates.json` 与报告中的资金结论一致
3. 缺失数据场景下 `risk_flags`/`data_degraded` 正确标注

### 6.3 工程

1. 不破坏现有 v2 工作流主路径
2. 新增字段有文档、有校验、有测试
3. 所有脚本在无新增依赖条件下可运行（或明确标注可选依赖）

---

## 七、风险与应对

1. 数据接口波动导致字段漂移
   - 应对：字段映射层 + 宽松解析 + 降级标记

2. 并发提升导致源站限流
   - 应对：并发上限、退避重试、失败隔离

3. 新增因子造成输出不稳定
   - 应对：先以“加分项”方式接入，不直接替代原有核心规则

---

## 八、版本结论

v3 的核心不是“功能堆叠”，而是“在固定时间预算内，稳定产出更高质量候选”。

优先级排序如下：

1. 性能优化
2. 三类资金数据
3. 主备数据源（后置）

该排序与当前业务目标一致：优先保证复盘时效与选股质量。
