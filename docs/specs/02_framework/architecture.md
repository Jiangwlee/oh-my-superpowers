# Architecture

本文档定义 oh-my-superpowers 的架构模型：四层结构、Agent 身份框架、质量评分表。

## 四层模型

```
┌─────────────────────────────────────────────────┐
│  Layer 4: CLI                                   │
│  omp 命令 + pi-<name> wrapper                   │
│  职责：安装/卸载/调用，路径解析                    │
├─────────────────────────────────────────────────┤
│  Layer 3: Agents                                │
│  agents/<name>.md（Pi frontmatter + prompt）    │
│  职责：角色身份、推理策略、输出约束、Skill 编排     │
├─────────────────────────────────────────────────┤
│  Layer 2: Skills                                │
│  skills/<name>/SKILL.md + references/           │
│  职责：告知 Agent WHEN 和 WHAT（不管 HOW）        │
├─────────────────────────────────────────────────┤
│  Layer 1: Tools/Scripts                         │
│  CLI 命令（bash/python/node）                    │
│  职责：实际执行能力，模型无需关心路径               │
└─────────────────────────────────────────────────┘
```

### 各层职责边界

| 层 | 负责 | 不负责 |
|----|------|--------|
| Tools/Scripts | 执行能力、结构化输出、错误提示 | 业务决策、推理 |
| Skills | WHEN（触发场景）、WHAT（调用哪个 CLI 命令）| HOW（脚本内部实现）|
| Agents | 角色身份、判断、推理循环、输出格式 | 底层执行细节 |
| CLI | 路径解析、安装管理 | 业务逻辑 |

### 关键约束

**Skills 中的脚本必须 CLI 化。**

弱模型（如 qwen3.5、kimi-k2）无法可靠解析 SKILL.md 中的相对路径。解决方案：

```bash
# 错误（弱模型会搞错路径）
bash scripts/fetch-market-emotion.sh 2026-03-21

# 正确（CLI 命令，路径透明）
pita data emotion 2026-03-21
```

SKILL.md 只写 CLI 命令文档，不写脚本路径。

## Agent 身份框架

### 核心原则

**Agent 必须有身份。** 如果无法将一个 Agent 映射到一个明确的角色（职业/职能），它最多只是一个 Skill。

### 身份三维度

| 维度 | 定义 | 测试问题 |
|------|------|---------|
| 专业角色（Role） | 一个人类可以担任的职位/职能 | "你是谁？"的答案像职业描述还是工具描述？|
| 决策自主性（Agency） | 存在无法脚本化的判断 | 这个 Agent 的每一步都是确定的吗？|
| 任务所有权（Ownership） | 对整个任务结果负责，而非某一步 | 结束后谁对结果"署名"？|

**公式**：`Agent = Role × Agency × Ownership`，三者任意一个为零 → 降级为 Skill。

### Agent 身份审问（4 个必答问题）

设计新 Agent 前必须回答，否则不允许进入开发：

```
1. 这个 Agent 的角色名是什么？（能用一个职业/职能描述吗？）
2. 它需要做哪些"无法脚本化"的判断？（至少列举一个）
3. 任务结束后，谁对结果负责？是 Agent 还是用户？
4. 如果换一个人来扮演这个角色，他们需要什么专业背景？
```

**判定规则**：
- 第 1 或第 2 题回答不出 → 这是 Skill 需求，不是 Agent 需求
- 答案中只有"工具"/"能力"/"功能"类词汇 → 重新思考定位

### 判断示例

| 需求 | 判定 | 理由 |
|------|------|------|
| "帮我读 PDF" | Skill | 完全可脚本化，无角色，无判断 |
| "帮我搜集市场信息" | Skill | 机械任务，用工作流替代 |
| "股市情绪分析师" | Agent | 有专业视角，判断"信什么/看什么" |
| "跨平台调研专员" | Agent | 决定"搜什么/够了吗/下一步" |
| "代码审查官" | Agent | 有质量标准，给出裁决和立场 |

### 虚假 Agent 的常见来源

- **把工作流当 Agent**："每天早上拉数据分析发报告" → Cron + Skills 组合
- **把能力扩展当 Agent**："帮我读 PDF 的 Agent" → 套壳无意义

## 质量评分表

### Skill Scorecard

| 维度 | 等级 | 评估标准 |
|------|------|---------|
| Spec 合规性 | 必过 | YAML frontmatter 完整；目录结构符合规范；name 与目录名一致 |
| Description 触发质量 | 高 | 触发边界清晰；无歧义；覆盖主要使用场景 |
| 指令质量 | 高 | 渐进式披露（不一次塞满）；有 Workflow；有 Guardrails |
| 脚本设计 | 高 | CLI 化（有 --help）；结构化输出；错误消息面向 Agent |
| 测试覆盖 | 中 | 至少 T1 静态检查；引用的文件全部存在 |

**使用方式**：配合 `skill-review` skill 执行审查。

### Agent Scorecard

| 维度 | 等级 | 评估标准 |
|------|------|---------|
| 身份清晰度 | 必过 | 能通过身份审问全部 4 题；角色名可用职业词汇描述 |
| 决策自主性 | 必过 | 至少一个无法脚本化的判断点，已在 prompt 中体现 |
| 任务所有权 | 高 | 输出有明确的署名结构（报告/裁决/分析结论）|
| Skill 集成 | 高 | 只通过 Skill CLI 调用外部能力；无裸脚本路径 |
| 约束设计 | 高 | 工具列表最小化；有输出模板；有迭代约束（如最少轮数）|
| 测试覆盖 | 中 | 有触发 eval；有输出质量 eval |

**使用方式**：配合 `agent-review` skill 执行审查（待建）。

## 测试三层

| 层级 | 内容 | 成本 | 何时运行 |
|------|------|------|---------|
| T1 静态检查 | 脚本语法、SKILL.md 机械合规、引用文件存在性 | 免费 | 每次提交前 |
| T2 E2E | `pi -p` 或 `claude -p` 跑真实 session，验证执行结果 | 有成本 | PR 前 |
| T3 LLM-as-judge | 用模型评分输出质量（清晰度/完整度/可操作性） | 低 | 评估迭代时 |

原则：T1 捕获 95% 的机械问题；T3 用于判断性评估；T2 做集成验证。
