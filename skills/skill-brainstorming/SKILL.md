# Skill Brainstorming

将模糊的 Skill 想法转化为完整的设计规格。

**核心工作方式：模型主动分析 → 提出具体建议 → 用户只需确认或纠正。**
不得把开放问题抛给用户。每次提问只问一件事，且必须附上模型自己的判断。

<HARD-GATE>
不得跳过 Phase 0 真实能力检验和 Phase 2 模式选择。
不得在用户批准设计规格之前生成任何文件或调用 writing-plans。
</HARD-GATE>

## 准备：加载基础知识

在开始前读取 `references/skill-fundamentals.md`，以其中的自治原则和判断标准为依据。

## Phase 0：真实能力检验（Hard Gate）

向用户提一个问题，然后自己推断后续判断：

> 你想封装的具体能力是什么？它依赖哪些工具、规范、脚本或私有知识？
> （例如："用 X CLI 工具做 Y"、"按内部编码规范审查 Z"）

收到回答后，**模型独立完成以下三项判断**，然后一次性给出结论：

1. **能力真实性**：是"封装模型无法直接完成的能力"，还是只是"让模型做 X"？
2. **必要性**：去掉这个 Skill，模型用通用知识能做到一样好吗？
3. **自治性**：这个 Skill 需要的所有知识，能否打包进自身的 `references/` 或 `assets/`？

给出结论格式：
> 我的判断：[通过/失败]
> 原因：[一句话说明]
> [如通过] 继续 Phase 1。
> [如失败] [告知具体失败原因，终止或建议调整方向]

**失败情形**：
- 只是"让模型做 X"，没有具体工具/规范依赖 → 终止，建议直接用模型
- 模型用通用知识已能完成 → 终止，不需要 Skill
- 存在无法内化的外部依赖（依赖其他 Skill、项目文件、Agent）→ 终止，需要先将依赖内化到 `references/`

## Phase 1：能力定义

基于 Phase 0 的分析，**模型主动起草**能力边界描述，请用户确认：

> 我对这个 Skill 的能力边界理解如下：
> - 它让模型能够：[一句话]
> - 能做：[列举 2-3 项]
> - 不能做：[列举 1-2 项]
> - 自治确认：所有判断标准和模板均可打包进 `references/` / `assets/`
>
> 这个描述准确吗？

等用户确认或纠正后继续。

## Phase 2：模式选择（Hard Gate）

加载 `references/design-patterns.md`，**模型主动推荐**最适合的模式，说明理由，请用户确认：

> 根据你描述的能力，我推荐 **[模式名]** 模式。
> 理由：[1-2 句说明为何匹配]
> [如果有竞争方案] 另一个候选是 [模式名]，但 [排除理由]。
>
> 你认同这个模式选择吗？

5 种模式速查（仅作参考，模型应主动判断，不应让用户自己选）：

```
Tool Wrapper  — 让模型成为特定技术/库的专家，动态加载规范
Generator     — 从模板生成结构化文档/代码，模板驱动输出
Reviewer      — 按标准检查内容，按严重程度分类
Inversion     — 先多轮收集需求再行动，有门控机制
Pipeline      — 严格的多步骤工作流，带检查点和用户确认
```

模式可以组合。确认后继续 Phase 3。

## Phase 3：结构设计

加载 `references/design-patterns.md` 中选定模式的目录结构，**模型主动提出**文件组织方案：

> 基于 [模式名] 模式，我建议以下目录结构：
> ```
> skill-name/
> ├── SKILL.md
> ├── references/
> │   ├── [文件名] — [用途]
> │   └── [文件名] — [用途]
> └── assets/
>     └── [文件名] — [用途]
> ```
> [如有脚本] scripts/ 下需要 [脚本名]，用于 [用途]。
>
> 这个结构满足需求吗？

## Phase 4：CLI 化设计

**仅当结构中包含 `scripts/` 时进行此阶段**，否则跳过。

模型主动提出脚本的 CLI 接口方案，请用户确认：

> 根据需求，我建议脚本接口如下：
> ```
> [command] [--flags] <args>  →  [输出格式]
> ```
> SKILL.md 中只写命令名，不写路径（路径由安装机制处理）。
>
> 这个接口设计合理吗？

## Phase 5：触发边界设计

**模型主动起草** description、Use when、Do NOT use when，请用户确认：

> 我起草的触发边界如下：
>
> **description 首句**：[核心价值，一句话]
>
> **Use when**：
> - [场景 1]
> - [场景 2]
>
> **Do NOT use when**：
> - [排除场景 1]
> - [排除场景 2]
>
> [如有重叠] 注意：这与 [已有 Skill 名] 有潜在重叠，区分方式是 [说明]。
>
> 这个触发边界准确吗？

## Phase 6：渐进式披露规划

**模型主动提出**内容分配方案：

> 我建议内容按以下方式分配：
>
> **SKILL.md body**（触发后立即需要）：
> - [内容项]
>
> **references/**（按需加载）：
> - [文件名]：[内容描述，何时加载]
>
> **assets/**（模板，按需使用）：
> - [文件名]：[用途]
>
> 这个分配合理吗？

## Phase 7：规格生成

加载 `assets/skill-design-template.md`，填写各节内容，写入：

```
docs/design/YYYY-MM-DD-<skill-name>-design.md
```

写完后：

> 设计规格已写入 `<path>`，请确认无误后我们继续制定实现计划。

等待用户确认，然后调用 **writing-plans** skill。

---

## 关键原则

- **模型主动，用户确认** — 每个 Phase 都是模型给出判断，用户只需说"同意"或"不对，应该是…"
- **一次一件事** — 每轮只问一个确认，不堆叠多个问题
- **Skill 自治** — Skill 只依赖自身目录内的文件；所有判断标准必须内化到 `references/`（详见 `references/skill-fundamentals.md`）
- **Phase 0 和 Phase 2 不可跳过** — 能力检验和模式选择是所有后续设计的基础
- **CLI 化按需** — 只有 `scripts/` 目录下有脚本时才做 Phase 4
- **规格优先于实现** — 设计文档批准前不生成任何代码文件
