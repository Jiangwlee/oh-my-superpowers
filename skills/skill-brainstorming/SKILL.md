# Skill Brainstorming

<!--
  用途：skill 设计前置检验，生成种子上下文后移交 brainstorming skill
  流程：探索项目 → 加载知识 → 能力检验 → 模式选择 → 构造种子 → 移交 brainstorming
  关键引用：
    - references/skill-fundamentals.md   自治原则和判断标准
    - references/design-patterns.md      5 种模式定义和目录结构
-->

skill-specific 前置检验器。只做 brainstorming 无法替代的两件事：**真实能力检验** 和 **模式选择**。通过后构造种子，移交 brainstorming skill 完成完整设计流程。

<HARD-GATE>
不得跳过能力检验和模式选择。
不得在移交 brainstorming 之前生成任何设计文档或代码文件。
</HARD-GATE>

## Checklist

Create a task for each item and complete them in order:

1. **探索项目上下文** — 了解项目现状，为后续检验提供依据
2. **加载基础知识** — 读取 references/skill-fundamentals.md 和 references/design-patterns.md
3. **能力检验** — 基于探索结果，验证是否为真实能力需求
4. **模式选择** — 推荐最适合的设计模式
5. **构造种子并移交 brainstorming**

## Step 1：探索项目上下文

开始对话前，**先做项目探索**，不要直接提问。至少检查：

- 已有 skill 列表（`skills/` 目录）和它们封装的能力
- 项目结构、CLAUDE.md、近期 commits
- 用户描述中提到的工具、脚本、CLI 或规范文件
- 是否已有类似能力的 skill（避免重复封装）

**探索的目的**：
- 理解项目当前的 skill 生态，找出空白和重叠
- 发现用户需求涉及的具体工具/规范/脚本，为能力检验准备论据
- 预判能力真实性和适合的设计模式

## Step 2：加载基础知识

读取 `references/skill-fundamentals.md` 和 `references/design-patterns.md`。

## Step 3：能力检验（Hard Gate）

**核心原则：基于探索结果检验，不问已知信息，不问空洞的开放式问题。**

### 检验策略

**先展示探索发现，再做针对性求证。**

典型模式（按需选择，不是固定流程）：

**当探索已能识别具体工具/规范时（推荐）：**
> 我看了项目现状：[简述发现]。
> 你要封装的核心能力是 [预判，如"用 X CLI 做 Y"]，依赖 [具体工具/规范]。
> 这个理解对吗？有没有我遗漏的依赖？

**当探索发现已有类似 skill 时（主动挑战）：**
> 我注意到已有 `[skill-name]` 封装了 [能力描述]。
> 你的需求和它的区别在哪？是扩展已有 skill 还是需要独立的新 skill？

**当探索发现可能不需要 skill 时（主动挑战）：**
> 你描述的需求，模型用通用知识就能完成——[具体理由，如"X 是公开的标准库，无需封装"]。
> 有没有模型做不到的部分？（私有规范、特定 CLI、内部流程等）

**当探索信息不足时：**
> 我看了项目结构，但对你要封装的能力还缺少关键信息。
> 它依赖哪些具体工具或私有知识？（例如："用 X CLI 做 Y"、"按内部规范审查 Z"）

### 判断维度（模型内部评估）

收集到足够信息后，模型**自行评估**三项：

1. **能力真实性**：是"封装模型无法直接完成的能力"，还是只是"让模型做 X"？
2. **必要性**：去掉这个 Skill，模型用通用知识能做到一样好吗？
3. **自治性**：这个 Skill 需要的所有知识，能否打包进自身的 `references/` 或 `assets/`？

### 判定输出

> 我的判断：[通过 / 失败]
> 能力真实性：[通过/失败] — [引用探索中发现的具体工具/规范]
> 必要性：[通过/失败] — [说明模型通用知识为何不足]
> 自治性：[通过/失败] — [说明依赖能否内化]
>
> [通过] 继续模式选择。
> [失败] [具体失败原因，引用探索发现，建议调整方向或终止]

**失败情形：**
- 只是"让模型做 X"，没有具体工具/规范依赖 → 终止，建议直接用模型
- 模型用通用知识已能完成 → 终止，不需要 Skill
- 存在无法内化的外部依赖（依赖其他 Skill、项目文件、Agent）→ 终止，需先将依赖内化到 `references/`

## Step 4：模式选择

基于 `references/design-patterns.md` 和探索结果，**模型主动推荐**最适合的模式：

> 根据 [引用探索中发现的具体特征]，我推荐 **[模式名]** 模式。
> 理由：[1-2 句，引用探索中的具体发现说明为何匹配]
> [如有竞争方案] 另一个候选是 [模式名]，但 [排除理由]。
>
> 你认同这个模式选择吗？

5 种模式速查：

```
Tool Wrapper  — 让模型成为特定技术/库的专家，动态加载规范
Generator     — 从模板生成结构化文档/代码，模板驱动输出
Reviewer      — 按标准检查内容，按严重程度分类
Inversion     — 先多轮收集需求再行动，有门控机制
Pipeline      — 严格的多步骤工作流，带检查点和用户确认
```

模式可以组合。模型应主动判断，不应让用户自己选。

## Step 5：移交 brainstorming

用户确认模式后，构造种子并启动 brainstorming skill：

```
我已完成 skill-brainstorming 前置检验，结果如下：
- 能力检验：通过。[一句话说明封装了什么真实能力]
- 选定模式：[模式名]。[一句话说明理由]
- 项目上下文：[探索中发现的关键信息，如已有 skill 生态、相关工具/脚本]
请基于以上上下文继续 brainstorming 流程。
```

**重要：** brainstorming 接手后，澄清问题阶段应充分利用已知的模式信息和探索发现，
直接聚焦 skill 设计的具体细节（目录结构、触发边界、CLI 接口等），不重复能力检验。

---

## 关键原则

- **先探索再提问** — 不带上下文的问题是废话，探索是提问的前置条件
- **只问不确定的** — 探索已确认的信息不再追问，模型自行评估
- **一次一件事** — 每轮只问一个问题，不堆叠
- **展示发现再提问** — 先告诉用户你看到了什么，再基于此提问
- **模式可以组合** — 模型应主动判断，不让用户自己选
